What you are reading now travelled from my machine to your browser through the steps below. Each one tells you if I run it in production or if this was my first time using it. Click any step to see how it works and what you can try yourself.

The only way in. This machine has no public IP and no port open to the internet. HAProxy binds to loopback, and the tunnel dials out to Cloudflare, so the connection is always outbound.

# loadbalancer/haproxy.cfg.template
bind 127.0.0.1:${LB_PORT}

Cloudflare sits in front of it, so I can drop a request by country or by network before it reaches my machine at all. I filter my private services that way. This page I do not: anyone should be able to read it, wherever they are.

Try it: run dig demo.josenaranjo.website. You get Cloudflare's addresses, never mine. There is nothing to scan and no port to reach.

If the tunnel drops, the site is gone. Nothing else is holding it up. That is the trade I made on purpose.

The whole public surface. Rate limiting, client checks and routing all happen here, before a request reaches any application.

Three separate rate limits

http-request deny deny_status 429 if { sc_http_req_rate(0,st_site) gt 300 }
http-request deny deny_status 429 if is_api { sc_http_req_rate(1,st_api) gt 30 }
http-request deny deny_status 429 if is_api { sc_http_err_rate(1,st_api) gt 20 }

The last one is the useful one. A wrong token comes back 401 from the application; HAProxy counts those, and once a client has 20 of them in five minutes it stops forwarding the requests at all and answers 429 itself. A guesser is out on the error counter, not the request one.

Sec-Fetch-Site is the strongest check: every current browser sends it, and page JavaScript is forbidden from setting it. This filters, it does not authenticate. Reading the page is meant to be open; the one thing that needs a credential is the chat, and that is the token in your link.

Try it, from any terminal: curl -i https://demo.josenaranjo.website/api/session -d '{}'. You get 403. Add -A "Mozilla/5.0" and you still get 403. The page itself answers 200 to the same curl. Only the API is closed to scripts.

The rate limits are quieter than they look. One reload of this page is three requests, fourteen if you force it past the cache, so 300 a minute is aimed at a script rather than at you.

Also here

  • every request gets a uuid, logged and passed on as X-Unique-ID
  • HAProxy cuts the session token out of the path before anything reaches a log
  • stats page and 423 Prometheus metrics on a second frontend, loopback only
  • the config is a template: envsubst, then haproxy -c, so a bad value stops the container instead of shipping a broken edge

Serves this page and answers the chat, in one process. It is also the only thing allowed to talk to the model. It holds the sessions and the refusals. The persona asks the model to behave; the backend does not depend on it.

There is no web server in front of it. express.static serves the four static files, which saves a container and a config template.

GET  /?chat_bot_token=<token>        widget renders
POST /api/session {chat_bot_token}   constant-time compare
                  → session = <expiry>.<nonce>.<HMAC>
POST /api/chat/<session>             verify HMAC + expiry

Every request is stateless. Conversation history never goes to the model, so nothing said earlier can steer a later answer. The backend cuts every answer after four sentences.

Try it: open this page again with the ?chat_bot_token=… part cut off your link. Same page, no chat. Nothing builds the widget, and the backend would refuse a session anyway.

The two containers are no longer containers. They are two Deployments in a hire-jose namespace on a real cluster, and the tunnel points at a NodePort instead of at docker.

chat-api       ClusterIP  :3000
loadbalancer   NodePort   :8080 → 30080   ← the tunnel lands here

GitHub Actions builds both images, pushes them to GHCR and writes the new tag into the manifest. That commit is the deploy. floci has an emulated ECR and I do not use it: it serves plain HTTP, and containerd insists on HTTPS.

The one that cost me an evening

Every pod DNS lookup timed out and nothing logged an error. br_netfilter was not loaded on the host, so bridged pod traffic never passed through iptables and kube-proxy's ClusterIP rules never fired. The node container cannot load it itself; the module has to be on the host.

Ollama stays outside the cluster on purpose. A 4.7 GB model on an 8 GB laptop GPU does not want to be scheduled.

Try it: ask the assistant for the ArgoCD login. It hands you a read-only account, and the resource tree you see there is the live one: the two pods answering you right now.

Nothing here is deployed by hand. An Application watches the k8s/ folder of the public repo with selfHeal and prune on, so the cluster follows the branch and anything I change locally gets reverted.

The theme you are looking at is the demo

# k8s/20-chat-api.yaml
- name: SITE_THEME
  value: "default"   ← one word. commit it, push it.

That is the whole change. No kubectl, no pipeline. ArgoCD notices the commit, rolls the Deployment, and the page goes from dark to light on its own.

Try it: ask the assistant to switch the theme: "make the site light". It writes that one word, pushes the commit, and answers with the link to it plus the ArgoCD login so you can watch the sync. Give it a few minutes and reload: this page comes back in the other palette.

I publish the UI read-only: a dedicated account bound to ArgoCD's built-in role:readonly. It can read the app; sync and delete both come back 403 permission denied. The commit is the only way in, for you and for me.

I created the cluster above with the AWS CLI, against an emulator running on this machine. There is no AWS account anywhere in this and the credentials are the string test.

aws eks create-cluster --name hire-jose   # → starts a real k3s container
aws eks update-kubeconfig --name hire-jose

It emulates the AWS API, so the EKS call is real and the Kubernetes behind it is real. None of that proves anything about running EKS. The AWS I run at work is the other kind: S3, Transit Gateway, Site-to-Site VPN, and Terraform-provisioned PrivateLink.

Nothing to click on this one: the emulator listens on localhost and is not published. You are already looking at its output, though. The cluster every hop above runs in is the one that create-cluster line started.
